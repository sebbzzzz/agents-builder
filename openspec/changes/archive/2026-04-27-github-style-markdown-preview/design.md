## Context

`RenderedView.tsx` currently applies `prose prose-invert prose-sm max-w-none` Tailwind classes to the markdown output container. However, `@tailwindcss/typography` is not in `package.json`, so these classes resolve to nothing — the rendered view is unstyled plain text with no visual hierarchy.

The app uses a warm dark theme (near-black backgrounds, orange accent) defined entirely in `globals.css` via CSS custom properties. Tailwind v4 is used without a separate config file.

## Goals / Non-Goals

**Goals:**
- Make the preview view render markdown with GitHub-flavored visual hierarchy: heading sizes, inline code styling, fenced code blocks with background, blockquotes with left border, tables, horizontal rules, list indentation, and link colors.
- Keep the dark theme consistent with the app's warm near-black palette.
- Zero new runtime dependencies.

**Non-Goals:**
- Syntax highlighting inside code fences (no rehype-highlight or prism — out of scope).
- Full GitHub.com pixel-perfect replication (font family, exact spacing).
- Light mode variant.

## Decisions

### Pure CSS in `globals.css` over `@tailwindcss/typography`

**Decision**: Write a `.markdown-body` `@layer components` block in `globals.css` instead of installing `@tailwindcss/typography`.

**Rationale**: 
- AGENTS.md instructs not to add dependencies without asking. This change needs no approval gate.
- The typography plugin would be overkill — we only need dark-mode prose styles, not the full plugin surface.
- A handwritten block is ~80 lines, gives full control over each element, and integrates directly with the app's existing CSS custom property tokens.

**Alternative considered**: `github-markdown-css` npm package (sindresorhus). Ruled out because it requires a new dependency and imports a full stylesheet that conflicts with the app's custom color tokens.

### Use app color tokens, not GitHub's literal hex values

**Decision**: Map GitHub's visual intent to the app's existing CSS variables (e.g., `--foreground`, `--border`, `--accent`, `--surface`) rather than hard-coding GitHub's exact colors.

**Rationale**: The app is warm-dark, not GitHub's cool-dark. Copying GitHub's hex values verbatim would clash with the existing UI. The visual hierarchy (not the palette) is what matters.

### Keep `react-markdown` as-is; no additional rehype/remark plugins

**Decision**: The existing `react-markdown` setup is sufficient. Styling is purely CSS — no plugin changes needed.

**Rationale**: Adding `rehype-raw` or `remark-gfm` introduces more deps. The markdown content generated by this app is structured and doesn't need raw HTML passthrough.

## Risks / Trade-offs

- **CSS specificity conflicts** → Use `.markdown-body` as a scope prefix on all rules (`.markdown-body h1`, `.markdown-body pre`, etc.) to avoid leaking into the rest of the app.
- **Tailwind v4 purging** → Since the class is written in `@layer components` inside `globals.css`, it will always be included. No purge risk.
- **Future typography plugin adoption** → The handwritten block can be deleted and replaced with the plugin later with no breaking changes to the component.
